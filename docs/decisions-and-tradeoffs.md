# 선택과 트레이드오프

| 결정 | 선택 이유 | 남는 비용·한계 |
| --- | --- | --- |
| 문서 + output 중심 공유 | 업무 문제·Tool 경계·판단 근거·관찰 결과를 설치 없이 읽고 평가 가능 | 실행 코드 없이 LLM 선택과 환경을 독립 재현할 수 없음 |
| 실행 앱은 별도 보존 | 기존 검증 경로를 잃지 않고 공개 범위를 줄일 수 있음 | 문서와 구현 버전의 연결을 해시/기록으로 관리해야 함 |
| 고정된 업무 Tool + 자연어 선택 | 호출 범위·오류를 검증하면서 여러 표현과 후속 조회를 지원 | 허용 Tool 밖의 새 업무는 코드·계약을 추가해야 함 |
| 계산은 코드, 선택은 모델 | 모델의 산술/식별값 환각과 업무 판단을 분리 | 집계 정의를 먼저 합의하고 검증해야 함 |
| 로컬 모델 | 합성 질의의 실행을 로컬에서 관찰 가능 | 이 관찰에서 약90초가 걸렸으며 품질·환경 차이가 있음. 개발 전 과정의 외부 처리가 없다는 증거는 아님 |
| 직접 Tool Calling | 도구4개와 단일 호출 루프의 경계를 이해·검증하기 쉬움 | 복잡한 상태 관리나 장시간 작업은 별도 설계가 필요 |
| MCP/에이전트 프레임워크는 보류 | 현재 단일 클라이언트와 소수 기능에 필요한 역할을 직접 구성 | 여러 클라이언트의 도구 재사용·외부 도구 생태계가 필요해지면 재평가 |
| 강습 수 상한 제거 | 전체 범위를 일부로 축소하지 않고 분석 | 전체 시간·메모리·자원 제어는 별도 과제이며 인터넷 서비스 운영성을 입증하지 않음 |
| output 출처를4종으로 구분 | 기대값·실행 관찰·모의 화면을 혼동하지 않음 | 문서 작성/갱신 시 기록과 구현 변경을 맞춰야 함 |

## 검토한 공유 방식

- 문서만: 공개 범위가 작지만 작동 증거가 약함.
- 실행 앱 전체: 독립 실행에 유리하지만 모델·의존성·환경 설정과 공개 범위 유지 부담이 큼.
- 문서 + 출처 있는 output: 현재 공유 형식으로 선택. 필요한 산술 입력과 Tool 스키마를 함께 두어 읽을 자료와 검증 가능한 주장을 연결.

이 선택은 구현 난이도를 감추거나 조직 정책 확인을 대신하기 위한 것이 아닙니다. 실행 장소·장비 사용·도구/산출물 공개 권한은 별도의 증거가 필요합니다.
